# Key Picker Scroll and Transparent Assignment Design

## 目的

キー割り当て画面の候補一覧を、800×600を含む高さの限られた画面でも最後までスクロールできるようにする。システム候補の「透過（Trans / TRNS）」を見つけやすくし、選択すると既存のキーマップ編集フローへ正しいbindingが渡る状態にする。

## 現状と原因の切り分け

- `SystemTab` には既に `Transparent` が登録され、クリック時は `{ behaviorId, param1: 0, param2: 0 }` を `onApplyBinding` へ渡している。
- `PickerTabs` にも `overflow-y-auto` は存在するが、現在のテストはクラス名とコールバックだけを確認し、実際の高さ、`scrollHeight`、フッターとの重なりを検証していない。
- 実画面ではシステム候補の末尾がフッター付近で切れ、ユーザー操作で「透過」へ安定して到達できない。
- `SystemTab` は許可名でfilterするだけなので、表示順がfirmware/APIの応答順に左右される。意図した配列順と画面上の順序が一致せず、「透過」が下へ移動する場合がある。

したがって、binding生成やRPCを作り直すのではなく、production layoutのスクロール境界と候補順を直す。実装前のREDとしてブラウザ上の幾何条件を再現し、最初に高さが途切れる祖先だけを最小修正する。JavaScriptでwheelイベントを横取りする回避策は採用しない。

## 採用する設計

### 1. 候補一覧を唯一の縦スクロール領域にする

- タブバー、「現在の設定」、アプリのフッターは固定したままにする。
- 候補一覧コンテナだけが残りの高さを受け取り、縦方向へスクロールする。
- `RightUsbEditorShell` → `StudioTabView` → `KeyboardWorkspace` → `Keyboard` → `BehaviorBindingPicker` → `PickerTabs` の高さ連鎖をブラウザで測定し、最初に `min-height: auto` または実高さ超過が起きる境界へ `min-h-0` / `minmax(0, 1fr)` / `overflow-hidden` のいずれか必要な最小変更を行う。
- 候補一覧には末尾余白を設け、最後の候補の下端がフッター上端より最低8px上に入るようにする。
- スクロール領域はフォーカス可能かつ名前付きにし、マウス・トラックパッドに加えてキーボードのPageDown/矢印操作でも移動できるようにする。
- タブ切替時に `scrollTop = 0` へ戻す既存動作は維持する。

### 2. 「無効」と「透過」を先頭へ固定する

- システム候補は `systemBehaviorNames` の優先順で並べる。
- 先頭は必ず `None`、次に `Transparent` とし、その後に他のシステム候補を並べる。
- firmware/APIが返していないbehaviorは合成しない。`Transparent` が応答にない場合、存在しないbehavior IDを作らない。
- Bluetoothのパラメータ付き操作は現在どおり別セクションに残す。

これにより、スクロール自体を直しつつ、最も頻繁に使う「透過」へ短い移動で到達できる。

### 3. 既存の割り当て・保存フローを使う

データの流れは次のまま維持する。

1. `SystemTab` が `Transparent` の実behavior IDを見つける。
2. クリック時に `{ behaviorId, param1: 0, param2: 0 }` を生成する。
3. `PickerTabs` から `BehaviorBindingPicker` の既存コールバックへ渡す。
4. `Keyboard` の既存編集処理がローカルキーマップとdirty状態を更新する。
5. ヘッダーの既存「保存」でデバイスへ保存する。

新しいRPC、proto、Firmware変更は行わない。クリック直後は「現在の設定」に「透過」が表示され、保存前の変更として扱われる。

## エラーと境界条件

- `Transparent` がbehavior一覧にない場合はボタンを表示せず、無効なIDでの割り当てを行わない。
- 候補数が少なくスクロール不要な場合も、余白や固定領域が不自然に広がらないこと。
- 800×600と1200×800の両方で、キーボード領域・候補領域・フッターが重ならないこと。
- タブ変更、キー選択変更、OSモード変更で候補一覧のスクロール所有者が外側へ移らないこと。
- 透過の選択は既存のUndo/破棄/保存対象に含め、直接保存や自動保存を追加しない。

## テスト設計

### Vitest（コミットする回帰テスト）

- API応答順が入れ替わっていても「無効」「透過」が先頭2件になる。
- 「透過」を押すと実behavior IDと0パラメータ2個を渡す。
- `Transparent` がない場合はボタンを表示しない。
- 候補一覧が唯一の `overflow-y` 所有者で、外側・タブバーは縦スクロールしない。
- 候補一覧にフォーカス名、キーボード操作に必要な属性、末尾余白がある。
- タブ切替時の先頭復帰を維持する。

### Storybook / Playwright（実レイアウト検証）

- 既存の統合800×600 Storyを使い、キーを1つ選択してシステムタブを開く。
- Playwrightで候補領域の `clientHeight` と `scrollHeight` を測り、候補が多い時は `scrollHeight > clientHeight` であることを確認する。
- 候補領域上でwheelまたは `scrollIntoViewIfNeeded` を実行し、「透過」のbounding boxが候補領域内かつフッターより上へ入ることを確認する。
- 「透過」をクリックし、「現在の設定」が「透過」へ変わることを確認する。
- 1200×800でも同じ操作を行い、不要なページ全体スクロールやフッター移動がないことを確認する。
- PlaywrightはCodexの既存ブラウザ実行環境で検証し、この修正のためだけに新しいnpm依存を追加しない。

### 完了時の通常検証

- focused Vitest
- full `npm test`
- `npm run lint`
- `npm run build`
- Storybook build
- Playwright 800×600 / 1200×800
- Tauriに影響するlayout変更として `npm run tauri build`

## 非対象

- キーマップ画面全体のデザイン変更
- 独自スクロールバーの装飾
- Firmware、proto、RPCの追加・変更
- 透過以外のbehavior仕様変更
- 保存確認や通知の再設計
- 他設定画面のスクロール方式の一括変更

## 受け入れ条件

1. 800×600でシステム候補を最後までスクロールできる。
2. 「無効」「透過」がシステム候補の先頭2件に表示される。
3. 「透過」を選択すると現在設定へ即時反映され、既存の保存対象になる。
4. 最後の候補がフッターに隠れない。
5. ページ全体、タブバー、キーボード表示領域は候補スクロールに引きずられない。
6. Firmware/RPCを変更せず、既存UIの構成を維持する。
7. VitestとPlaywrightの両方で回帰を確認する。
